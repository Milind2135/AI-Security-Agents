# threat-modeler changelog

| Version | Date | Change |
|---|---|---|
| 1.0 | 2026-11-17 | Draft only — never moved into place; superseded by 1.1 the same day. New agent. Builds an evidence-backed threat model of one system from code, IaC and design documents. Procedure: Step 0 preflight with help card (`?`) and scope routing; Step 1 discover (coverage log; BR/U/A/C/EE/DS IDs; asset criticality rules; deployment, integrations, existing controls and known risks); Step 2 model (data flows, trust boundaries wherever identity/privilege/zone/ownership/tenant/platform changes, integration assessment for every boundary-crossing flow, Mermaid DFD); Step 3 analyse (STRIDE-per-element plus injection, abuse cases, social engineering and AI/LLM threats; logging/repudiation checks incl. AI agent actions; request-flow tracing through middleware before rating auth threats; vulnerabilities with CWE category; fixed likelihood/impact/risk/priority rules with a single threat-intel bump); Step 4 verify (six control statuses incl. `Claimed` and `Not effective here`; four threat statuses; assumptions register; eight-question completeness check; human review load with a default limit of 15); Step 5 one-message report with 13 sections; Step 6 JSON handoff to risk-analyst, detection-engineer, devsecops-engineer and cloud-security-analyst. Portable from the start: tool roles for Claude Code, Copilot, Codex and Cline (legacy); entry files `.claude/agents/threat-modeler.md` and `.codex/agents/threat-modeler.toml`. Synthetic golden tests in `tests/threat-modeler/`. Design agreed with the owner on 2026-11-17; wording original. |
| 1.1 | 2026-11-17 | Draft only — superseded by 1.2 the same day before release. **Intake step:** by default the agent first asks a 25-question questionnaire in four tiers (minimum, evidence, context, specialist), pre-filling items already covered by the supplied material, then stops; answers (pasted or a filled `docs/threat-model-intake.md`) or `intake: skip` let it proceed; at most one questionnaire. Section 2 gains an intake checklist with statuses `Provided` / `Derived` / `Not provided` (with the effect of the gap) / `Not applicable`. **New context inputs and how they are used:** diagrams as images (controls in diagrams are `Claimed`); data classification and essential functions feed impact; compliance scope marks controls `Mandatory (<regime>)` without quoting unfetched clause numbers; security standards are cited and their violations become `V-#`; risk owner and appetite (appetite informs, never accepts); prior pentest/scanner/bug-bounty findings re-checked as `Still present` / `Fixed` / `Cannot verify`; incident history joins threat intelligence as a source for the single priority bump; AI details, operational processes (account recovery abuse), change delta, feature flags and client-application threats. Deterministic overall-confidence rule. JSON gains `owner`, `intake`, `compliance`, `prior_findings`, and `standard`/`mandatory` fields. Tests: `intake: skip` for tests 1–6, new test 8 (questionnaire) and test 9 (intake with GDPR, standards, owner, prior pentest).
| 1.2 | 2026-11-17 | Draft only — superseded by 1.3 the same day before release. **Readiness check** after discovery (always runs): `Not ready` stops with the 3–5 most useful missing items; `Proceed with limits` when no code or IaC (confidence Low); `Ready`. **DFD review checkpoint** (default `checkpoint: review`): after building the model the agent sends a "model for review" message — Mermaid DFD, element tables with a Source column (code/IaC/doc/diagram/intake/inferred, inferred listed first), assumptions, up to 5 questions and a model JSON — and stops; replies `approve — <name, role>` (recorded as given, not verified), corrections (`MR-#`, next round, max 3) or `skip review`; `checkpoint: skip` for quick reviews and tests. Approved model is the baseline; later additions marked `added after review`; approval never makes a control `In place`. High confidence now also needs an approved DFD. JSON gains `readiness` and `dfd_review`. Claude Code continuation via `model:` + `review:` inputs. Tests: `checkpoint: skip` for tests 1–6 and 9; new tests 10–12 (review, correction, approval changing a rating) and 13 (not ready, fixture `07-not-ready`).
| 1.3 | 2026-11-17 | First released version, after research (STRIDE GPT, AWS Threat Composer, Threat Modeling Manifesto, Threagile/pytm, continuous threat-modelling practice, LLM reliability studies — ideas only) and a full ambiguity review. **Ordered first-match rules** for likelihood (Low → High → Medium; self-registration counts as external), impact (High → Medium → Low; any availability loss of an essential function is High) and threat status (Mitigated → Partially mitigated → Unverified → Open). **Coverage matrix** (element × category, every applicable cell a T-# or `n/a — reason`) and a fixed **threat-statement** sentence with C/I/A. CWE names only (IDs if fetched). **DFD building:** one flow per hop with intermediaries as elements, direction/initiator and mode, identity carried and where authorisation is decided (confused-deputy flag), data journeys for High assets with where encryption ends and at-rest status, management path, secondary copies, third parties and residency, side channels, data lifecycle, AI flows, document/code **mismatches** `MM-#`, context + per-zone diagrams above 15 nodes. **Review message:** mismatches first, prioritised questions; model JSON carries the intake so continuation needs only `model:` + `review:`. **Verification:** re-open cited lines for Critical/High and Mitigated items; model quality check. **Report:** 14 sections; preventive + detective controls for Critical/High; "How to verify" per control; mandatory-compliance basis; what to save for a living model. **Follow-up:** `decisions:` recorded verbatim (incomplete accepts flagged, unmatched IDs listed, never changes ratings), ticket drafts (`ticketing: off|draft`), **recheck** with stable IDs and Fixed / Still open / Changed / Not re-assessed / New. Tests 14–16 and fixture `08-payments-multihop` added. **Analysis phase restructured in the owner's order (same day, before release):** 3a threats (entry points, fixed attacker types, depth by focus tier, per-element and per-interaction STRIDE, checklist prompts per category, supply chain, device element, abuse cases from requirements, assumption tests, privacy threats only for High personal data or a named privacy regime, primary/secondary STRIDE by security property, weakness-name labels, de-duplication, chaining) → 3b vulnerabilities → **3c existing-control validation** (ordered tests: exists, on the path, fits the platform, evidence with request-flow tracing, enforced, cannot be bypassed, still current, right identity, covers everything; plus 'acted on' for detective controls; first failed test named) → 3d risks (status, potential damage in business terms) → 3e classification (likelihood/impact with exploitability, location, asset criticality, business impact, validated controls) → 3f prioritisation (matrix, threat-intel bump, attack paths for Critical, grouping above 40 rows). Step 1 adds entry points and the crown-jewel and exposure profile; Step 2 adds focus tiers (A/B/C) shown in the DFD review. Report Sections 6–9 renamed: Threats (STRIDE summary, register, compact coverage matrix), Vulnerabilities, Existing Control Validation, Risks — Classification and Prioritisation; CSV block of the register for spreadsheets. **Labelling, deployment and critical interactions (same day, before release):** one label format for every element (`ID · name · type · tier · trust zone`) and every flow (`DF-#: data · protocol · identity`); DFD shapes by element type, thick arrows for critical flows, a legend, and Mermaid syntax rules verified to render (underscore node IDs, quoted labels); deployment view `D-#` per component, deployment pipelines `P-#` (trigger, who can deploy to production, signing, secrets injection, manual changes; pipelines are Tier A), environment separation and a separate deployment diagram, all shown in the DFD review; critical interactions `★` by a fixed rule (boundary crossing with crown-jewel data, privileged action or external initiator; or confused-deputy hop, plaintext crown-jewel segment, third-party transfer), listed in the review and Section 4 and always analysed per interaction; completeness check for missing labels, deployment rows and unanalysed critical interactions. **Treatment and follow-through (same day, before release):** new Step 3g — all four treatment options (mitigate, avoid, transfer, accept) per risk without choosing, and residual risk now / with compensating controls / after recommended controls; developer-ready security requirements with 2–4 testable acceptance criteria for every control on a Critical/High risk (carried into ticket drafts); framework references by name only (OWASP ASVS, NIST SP 800-53 families, CIS Controls) unless fetched; compensating (temporary) controls via `compensating:`, intake or material — validated like any control (stated-only → `Claimed`), owner + end date + permanent fix required (else `incomplete`; past end date → `expired`), never a replacement for the permanent fix. **Assumptions (same day, before release):** new Assumptions section — full register (`AS-#`, type incl. control and risk rating, basis, affects, if-wrong, how to confirm and by whom, status Open/Confirmed/Rejected); eight mandatory logging triggers; cautious-assumption rule (unknown → control absent, element reachable; never lowers a risk); `AS-#` tags beside dependent control results and ratings; open assumptions affecting Critical/High risks in Section 1 and open questions; DFD review asks about the highest-effect assumptions first; JSON assumption records. **Control driver (same day, before release):** proportionality principle written into Section 10 (value and risk of what is protected, including harm to customers and third parties; mandatory and baseline controls regardless of business value); every recommended control gets exactly one Driver — Mandatory (regime) → Security baseline (standard ID) → Business requirement → Asset value → Risk, first that applies; mandatory and baseline controls never dropped for low business value. **Agent self-protection (same day, before release):** new guardrail group — read scope limited to supplied paths and named inputs (never answer keys or credential files); instruction hierarchy (conflicting user requests declined in one line, rest continues); hidden-instruction handling across comments, invisible Unicode, encoded strings, metadata, intake answers and JSON values (reported, never decoded-and-obeyed); validation of `model:`, `previous:`, `decisions:` and `compensating:` (malformed → treated as not supplied; JSON can never self-approve; `model:` without `review:` re-shows the review); no URLs or hosts taken from the material and no material content in URLs; data minimisation in the report (mask personal data, ≤ 3 lines of code per evidence item); no exploit code or payloads; no write/send tools. Diagram styling rule (red dashed trust zones, colour per element type). Tests 17–18 added. **Exporter (same day):** `tools/threat-modeler-export/tm_export.py` turns a saved report into PNG/JPEG/SVG diagrams (styled trust boundaries, critical flows in red), `threat-model.xlsx`, `threat-model.json` and optional `report.docx`; diagrams tagged `%% diagram: dfd|deployment`; Section 13 points to it.
